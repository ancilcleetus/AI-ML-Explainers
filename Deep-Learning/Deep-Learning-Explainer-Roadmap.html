Residual Connections — How Gradients Flow Through Deep Networks — Interactive Explainer ↗
Why deep networks failed before 2015 and how a remarkably simple idea changed everything. The vanishing-gradient problem revisited from the angle of network depth: each layer multiplies its incoming gradient, and product of many small numbers vanishes. The residual connection — instead of having a layer compute H(x), have it compute F(x) = H(x) - x, then add x back: H(x) = F(x) + x. Why this helps: the gradient now has a guaranteed path back through the addition node, no matter how badly the F(x) branch is behaving. Visual demo: a deep network with and without residuals, gradient magnitudes plotted per layer during training; you can see the without-residual version's deep-layer gradients flatline. The general residual block design: two conv layers (or two fully-connected layers in our MLP context) wrapped with a skip connection. Pre-activation vs post-activation variants (PreActResNet vs ResNet v1). Why residual connections are now ubiquitous: every modern Transformer block contains them, every LSTM variant uses them, diffusion models use them, autoencoders use them. The conceptual takeaway: residuals are not a CNN trick, they are a deep-network technique that applies everywhere. Bridge from this conceptual treatment to the architecture-specific treatment in the ResNet — Residual Connections — Interactive Explainer in the Computer Vision Roadmap.

Layer, Group & Instance Normalization — Beyond BatchNorm — Interactive Explainer ↗
The family of normalization methods that don't depend on batch statistics — critical for Transformers, RNNs, small-batch training, and style transfer. Recap of what Batch Normalization (from the Batch Normalization — Interactive Explainer) actually normalizes — across the batch dimension, per-feature. The conceptual generalization — all normalization methods compute (x - μ) / σ, the difference is WHICH AXES μ and σ are computed over. Layer Normalization: normalize across all features for each sample independently. Why this matters: the result doesn't depend on batch composition, making it stable for small batches and ideal for RNNs and Transformers where each token is processed independently. Instance Normalization: normalize across spatial dimensions per sample per channel. Used heavily in style transfer (it removes per-image contrast/brightness, leaving only structural information). Group Normalization: split channels into groups, normalize within each group. The 'best of both worlds' compromise — independent of batch size like LayerNorm, but with per-group statistics for some of the channel-specific behavior of BatchNorm. The unified visualization: a 4D tensor (batch, channels, height, width) with overlay diagrams showing which slice each method averages over. Interactive: a slider for batch size showing how each method's behavior degrades or stays stable. The practical decision tree: when to use which normalization in 2026.

Early Stopping — When to Stop Training — Interactive Explainer ↗
One of the simplest and most effective regularization techniques — stop training before the model overfits. The motivation: the Overfitting & Generalization — Interactive Explainer showed that training loss keeps decreasing even as validation loss rises. Early stopping says: when validation loss stops improving, halt. The algorithm: track validation loss every epoch (or every K steps); if it hasn't improved for P epochs (the 'patience' parameter), stop training and revert to the best checkpoint. Interactive demo: train a real model with a live patience slider; watch the early-stop point move as you change patience. The trade-offs: small patience (P=1-2) can stop too early on naturally noisy validation curves; large patience (P=20+) wastes compute on probably-doomed training. Practical recommendations for setting patience based on dataset size, validation set noise, and learning-rate schedule interactions. The connection to checkpoint management — early stopping requires keeping the best checkpoint, not the last (covered in detail in the Checkpointing & Resuming Training — Interactive Explainer). Implementation in PyTorch: a simple class wrapping the validation-loss tracking and checkpoint revert logic. Common pitfalls: stopping based on training loss instead of validation; not separating early-stopping decision from learning-rate schedule decision; using too-noisy validation sets that produce false stops.

Network Depth, Width, and Capacity — Interactive Explainer ↗
The practical question every learner asks after building their first MLP: how many layers, how wide each, how does that scale? Parameter counting from first principles — a layer with 100 inputs and 50 outputs has 100×50 + 50 = 5050 parameters (weights plus bias). A 5-layer network with 256 neurons per layer has roughly 4 × 256² = 262K parameters. Interactive parameter calculator with sliders for depth and width. Capacity vs data: a 1M-parameter network trained on 100 examples will memorize; the same network on 1B examples will generalize. The classical bias-variance trade-off as a function of capacity. The modern surprise — Double Descent: as you keep increasing capacity past the interpolation threshold (where the model perfectly fits training data), test error first rises (the classical regime) and then falls again (the modern regime). Visual demo: plot test error vs model size on a fixed dataset, showing the iconic 'double descent' curve. Why this matters for modern DL — over-parameterized networks (millions of parameters trained on thousands of examples) generalize better than mildly-overparameterized ones, contradicting classical learning theory. Why does this happen — the lottery-ticket hypothesis and implicit regularization from SGD's choice of which solution to converge to. Practical recommendations for picking depth and width in 2026: start with a known-working backbone, scale width before depth, ensure your network is at least mildly overparameterized for your dataset size.

Train / Validation / Test Splits and Why They Matter — Interactive Explainer ↗
The three-way split rule every DL learner must internalize. Why three not two: a single train/test split is dangerous because you'll be tempted to tune hyperparameters on test, contaminating it as an unbiased measure. The clean three-way split: train (for learning), validation (for hyperparameter tuning and early-stopping decisions), test (for final unbiased evaluation, used ONCE). Standard ratios: 60/20/20 for small datasets, 80/10/10 for medium, 98/1/1 for very large datasets. The K-fold cross-validation alternative when data is very limited: split into K folds, train K times with each fold as validation; average results for a less-variance estimate. The 'train+val' final-model trick: once hyperparameters are chosen, retrain on train+val combined for the final model. Test contamination — the most common mistake in beginner ML, with examples of how easily it happens (looking at test set 'just to verify,' having test-set distributions leak through preprocessing decisions, etc.).

27
Input Preprocessing & Normalization — Interactive Explainer ↗
How raw inputs become network-ready tensors — the first step of any training pipeline. The fundamental problem: neural networks train poorly when input features have wildly different scales. A network seeing 'age' in 1-100 and 'income' in 10000-100000 will let the income gradient dominate everything until weights compensate, which takes a long time and may never converge cleanly. The two standard normalizations. Z-score (standardization): (x - mean) / std, gives output with mean 0 and std 1. Min-Max scaling: (x - min) / (max - min), gives output in [0, 1]. When to use which: z-score for inputs that are normally distributed and may have outliers; min-max for bounded inputs like pixel values (0-255 → 0-1). The crucial subtlety: compute statistics (mean, std, min, max) on the training set ONLY, then apply to validation and test. Computing them on the full dataset leaks information. Per-feature vs per-image normalization for images. The connection to Batch Normalization — Interactive Explainer: input normalization happens once before training (statistics fixed), BN happens dynamically inside the network (statistics recomputed per batch). The connection to Embeddings — Representing Discrete Data as Vectors — Interactive Explainer for categorical inputs. Practical recipes: tabular data (z-score continuous features, one-hot or embed categorical), images (divide by 255 or use ImageNet statistics for pretrained backbones), text (handled via tokenization + embedding, not classical normalization). Common pitfalls: applying normalization but storing un-normalized data; recomputing statistics on each batch by mistake; forgetting to apply test-time normalization with training statistics.

Data Augmentation Principles — Why and When — Interactive Explainer ↗
Artificially expand your training data by applying label-preserving transformations. The core idea: if a cat is still a cat when rotated 5 degrees, training on both the original AND the rotated version teaches the model rotation-invariance. Why this works as regularization: the network sees more 'different' inputs sharing a label, which forces it to learn the underlying signal rather than memorize specific pixel patterns. The label-preserving constraint: augmentations must not change the meaning. Horizontal flip of a face = still a face; horizontal flip of a '6' = '6' is wrong (becomes a '9'). Domain-by-domain treatment with examples. Images (covered in deep detail in the Computer Vision Roadmap): geometric (rotate, flip, crop), photometric (brightness, contrast, color jitter), composition (cutout, mixup). Text: random word deletion, synonym replacement, back-translation (translate to French and back). Audio: pitch shift, time stretch, additive noise, time masking. Tabular: feature noise injection, SMOTE for class imbalance. Time series: time warping, magnitude warping. The 'test-time augmentation' trick — apply augmentations at inference and average predictions for free 1-3% accuracy gain on most tasks. When NOT to augment: medical imaging where left-right asymmetry matters; legal text where word changes alter meaning; any task where transformations may not preserve labels. The connection to inductive bias — augmentation tells the model 'I want you to be invariant to this transformation.' The compute trade-off: augmentation costs CPU time; for huge datasets it may not be needed. Practical recommendations on which augmentations to start with for common domains.

Class Imbalance — When One Class Dominates — Interactive Explainer ↗
The reality of most real-world classification datasets and what to do about it. The problem: in fraud detection, only 1% of transactions are fraud; in medical diagnosis, only 5% are positive cases; in defect detection, only 0.1% are defects. A classifier trained naively achieves 99% accuracy by always predicting 'normal' — and is useless. Why default training fails: cross-entropy treats every example equally, so the rare class contributes 1% of the loss signal. The metric problem: accuracy is misleading on imbalanced data; you need precision, recall, F1, balanced accuracy, or AUC depending on the use case (deep dive in the Evaluation Metrics for Classification — Interactive Explainer). The fixes, in order of typical effectiveness. Class weighting in the loss: multiply each example's loss by a weight inversely proportional to its class frequency. PyTorch implementation: `torch.nn.CrossEntropyLoss(weight=class_weights)`. Oversampling the minority class: train multiple times on rare examples per epoch. PyTorch's WeightedRandomSampler. Undersampling the majority class: train on fewer common examples. Loses data, used less often. SMOTE (Synthetic Minority Over-sampling): generate synthetic minority examples by interpolating between real ones; works well for tabular, less so for high-dimensional image/text data. Focal loss (briefly): a modified cross-entropy that downweights easy examples and focuses on hard ones; used heavily in object detection. The 'cost-sensitive' framing — sometimes false positives and false negatives have different real-world costs, and the loss function should reflect that. Interactive demo: a 95/5 imbalanced classification problem trained with each technique, showing the precision-recall curves change.

DataLoader Performance — Workers, Pinned Memory, GPU Idle Time — Interactive Explainer ↗
The most common training bottleneck and how to fix it. The fundamental problem: GPUs compute fast (modern GPUs at 100+ TFLOPS), but data loading from disk or preprocessing on CPU is slow. Result: GPU sits idle waiting for data; training time is dominated by data loading. Symptoms: nvidia-smi shows GPU utilization < 50%; profiler shows DataLoader as the bottleneck. The PyTorch profiler workflow for diagnosing data-loading bottlenecks. The fixes, in order. num_workers > 0 in DataLoader: spawn N worker processes that prefetch the next batches in parallel while the GPU computes the current one. Rule of thumb: start with num_workers = 4 × num_GPUs. pin_memory=True: pre-allocate CPU memory in 'pinned' mode that can be DMA-transferred to GPU without an intermediate copy. Free 1-2x speedup on most setups. prefetch_factor: how many batches each worker prepares ahead of time. Higher = smoother but more memory. persistent_workers=True: don't kill and restart workers between epochs; saves the startup cost. Caching expensive preprocessing: if your augmentation or feature extraction is slow, cache results to disk after the first epoch. Memory-mapped files (numpy.memmap, HDF5) for large datasets. When to graduate to faster data formats: WebDataset for streaming, FFCV for ImageNet-scale throughput, MosaicML StreamingDataset for cloud-based training. The diagnostic workflow: profile first, identify the bottleneck (CPU? disk I/O? GPU transfer?), apply the matching fix. Common pitfalls: too many workers (system thrashing), num_workers=0 in production (single-threaded), forgetting pin_memory when GPU transfer is bottleneck.

Monitoring Training (Loss Curves & Diagnostics) — Interactive Explainer ↗
How to read a training curve and diagnose what's going on. The four canonical curve shapes. Healthy convergence: training and validation loss both decrease, validation tracking training closely until it plateaus. Overfitting: training loss keeps decreasing while validation loss starts rising — the model is memorizing rather than generalizing. Underfitting: both losses plateau at a high value — the model lacks capacity or training time. Divergence: loss explodes (often to NaN) — usually exploding gradients, wrong learning rate, or numerical instability in mixed precision. Interactive: a four-panel gallery showing each shape with sliders to perturb the run. What to log beyond loss. Gradient norms: per-layer gradient magnitudes; vanishing or exploding gradients show up here before they cause final-loss disasters (callback to the Vanishing & Exploding Gradients — Interactive Explainer). Learning rate (when using a schedule): visualize the actual LR over training, not the configured one. Per-parameter update ratios: the magnitude of update / magnitude of weight, should be around 1e-3 for healthy training. Throughput: samples per second; a sudden drop indicates an issue. The 'is my training actually working?' checklist for the first few epochs. Reading curves from the start: spike at step 0 (always; initial loss is high), rapid drop in first ~100 steps (good sign), plateau (concerning if early), then slow steady decrease (healthy training). Common pitfalls: looking only at the last epoch's loss; comparing models trained for different numbers of epochs; not logging validation loss frequently enough to catch overfitting; using log-scale when you should be using linear-scale (or vice versa) for the comparison you're trying to make.

Mixed Precision Training — AMP, fp16, bf16, and Loss Scaling — Interactive Explainer ↗
Train faster and with less memory using 16-bit floats. The hardware story: modern NVIDIA GPUs (Volta and later) have Tensor Cores that compute 16-bit matrix multiplies 4-8x faster than 32-bit. AMD MI series and Apple silicon have similar paths. The opportunity: if we can train in fp16, training is dramatically faster and uses half the memory. The problem with pure fp16: it has a smaller dynamic range than fp32 (max ~65504, min ~6e-8 normal). Gradients during deep-network training often underflow to zero, breaking training. Two solutions. fp16 with loss scaling: multiply the loss by a large number (e.g., 65536) before backward; this rescales gradients up into fp16's representable range. After computing gradients, divide them back down before applying the optimizer step. PyTorch's torch.cuda.amp.GradScaler handles this automatically including the 'check for inf/nan and skip step' logic. bf16 (bfloat16): same number of bits as fp16 but distributed differently — same dynamic range as fp32 (8 exponent bits), fewer mantissa bits (7 vs 10). bf16 doesn't need loss scaling, but is only available on newer hardware (A100 and later, H100, MI250+). The PyTorch AMP recipe: wrap forward and loss computation in `with torch.cuda.amp.autocast():`, wrap the backward+optimizer step with the GradScaler. When mixed precision helps most: large models, small models can sometimes be slower in fp16 due to overhead. When to use bf16 vs fp16: bf16 if you have the hardware, fp16 with loss scaling otherwise. Common pitfalls: forgetting GradScaler, applying autocast to the wrong code block, accumulating loss in fp16 (use fp32 accumulator).

Gradient Accumulation — Simulating Larger Batches — Interactive Explainer ↗
Train with effective batch size much larger than fits in GPU memory. The motivation: many techniques work best with large batches (e.g., LayerNorm-based Transformers prefer batch 256+), but a 7B parameter model with batch 256 won't fit on a single GPU. The trick: forward + backward 8 times with batch 32, accumulate the gradients in PyTorch's autograd buffers, only then call optimizer.step(). Effectively trains as if batch=256. The math: gradients of mini-batches sum (equivalently, average) to the gradient of the full batch — so accumulating 8 batches and stepping once IS the same as one step on batch 256 (up to numerical precision). The PyTorch idiom: do NOT call optimizer.zero_grad() every step; only every N micro-batches. Pseudocode: for i, batch in enumerate(loader): forward, loss = ..., loss.backward(); if (i+1) % N == 0: optimizer.step(); optimizer.zero_grad(). The careful detail: should you divide loss by N (so the total gradient magnitude is correct)? Usually yes. The interaction with BatchNorm — Interactive Explainer: each micro-batch uses its own statistics, which is statistically different from a true large-batch run. Not always a problem but worth knowing. The interaction with learning rate: effective batch size matters for LR choice; if you scale batch from 32 to 256 via accumulation, you typically scale LR by sqrt(8) = 2.83. When gradient accumulation matters: large language models (always), large vision models (often), distillation training (often). When it doesn't: small models, or when batch 32 is already large enough for your loss. Combined with Mixed Precision Training — Interactive Explainer for maximum memory savings.

Checkpointing & Resuming Training (and Activation Checkpointing) — Interactive Explainer ↗
Two distinct but commonly-confused techniques. Part 1: Saving and resuming training. Why checkpoint: training crashes (preemption, hardware failure, OOM); you want to save the best model not just the last; you want to compare epoch 50 vs epoch 100. What to save: model state_dict, optimizer state_dict (Adam's running averages matter!), scheduler state_dict, the AMP GradScaler state, the current epoch number, the best-so-far metric, RNG state for reproducibility. The save/load idiom in PyTorch with a complete code snippet. The 'save-best vs save-last' decision: save both. Best is what you deploy; last is what you resume from. The reproducibility trap: even with all state saved, resumed training is not bitwise-identical to non-interrupted training (due to floating-point non-associativity and CUDA non-determinism). Practical impact is small. Part 2: Activation Checkpointing (the unrelated thing also called checkpointing). The memory problem: forward pass stores activations at each layer for backward; this can be the dominant memory cost for deep networks. The trick: don't store some activations; recompute them during backward. Tradeoff: less memory, more compute (about 30% slower training). PyTorch's torch.utils.checkpoint API. When activation checkpointing makes sense: when you're memory-bound, want a larger batch, training a very deep network. When it doesn't: when you're compute-bound or memory isn't the limiting factor. The combination: AMP + gradient accumulation + activation checkpointing together can let you train a model that nominally requires 4x your GPU memory on the actual hardware you have.

Data Parallelism — Training One Model on Multiple GPUs — Interactive Explainer ↗
The most common form of distributed training. The mental model: replicate the model on each GPU, split the batch across GPUs, forward+backward independently, then synchronize gradients across GPUs before optimizer step. Worked example: 4 GPUs, batch_size_per_gpu=32, effective_batch=128. The synchronization step: an 'all-reduce' operation averages gradients across all GPUs so every GPU sees the same averaged gradient. NCCL (NVIDIA) and gloo (CPU) as the backend communication libraries. The all-reduce algorithm intuitively: ring-allreduce minimizes inter-GPU bandwidth by passing chunks around in a ring rather than sending everything to one place. Why this scales reasonably well: communication is overlapped with computation. While GPU is computing layer N's backward, layer N+1's gradient is being all-reduced in the background. Scaling efficiency: typically 90%+ for 2-8 GPUs on a single node, drops to 60-80% for multi-node setups due to slower interconnects. PyTorch DataParallel (legacy, single-process multi-GPU) vs DistributedDataParallel (modern, one process per GPU). Why DDP wins: avoids Python GIL contention, scales much better. Mentioned for completeness: PyTorch DataParallel exists but is essentially deprecated; never use it for new code. The learning-rate scaling rule: when going from 1 GPU at batch 32 to 8 GPUs at batch 256, you typically scale LR by 8 (linear scaling) for SGD or sqrt(8) for Adam. When data parallelism stops working: when the model itself doesn't fit on one GPU (then need model parallelism — see the Model Parallelism — Interactive Explainer).

Model Parallelism — When the Model Doesn't Fit on One GPU — Interactive Explainer ↗
The problem data parallelism can't solve: a 70B-parameter LLM has 140GB of fp16 weights, plus optimizer state, plus activations — total often 1TB+. No single GPU has that much memory. The solution: split the MODEL itself across GPUs, not the batch. Three flavors. Pipeline parallelism: split the model's LAYERS across GPUs. Layer 1-12 on GPU 0, 13-24 on GPU 1, etc. Data flows through them like a factory pipeline. The 'bubble' problem: when GPU 0 finishes layer 12 and sends to GPU 1, GPU 0 sits idle. Mitigation: micro-batches — split each batch into chunks so multiple chunks are in flight simultaneously, keeping all GPUs busy. GPipe (Google) and PipeDream (Microsoft) as landmark papers. Tensor parallelism: split individual operations across GPUs. A massive matmul Y = XW (where W is sharded across 8 GPUs in columns) becomes 8 smaller matmuls in parallel, with an all-gather to assemble the result. Megatron-LM (NVIDIA) pioneered this for Transformers. 3D parallelism: combine data + pipeline + tensor parallelism. This is how GPT-4-scale models are trained — 1000s of GPUs in a grid where each axis is one form of parallelism. Why model parallelism is harder than data parallelism: implementation complexity (must rewrite forward pass), communication patterns, debugging (failures appear in obscure places), interaction with other techniques. The practical takeaway: only use model parallelism when forced by model size; data parallelism is always preferred when possible. Brief mention of FSDP (Fully Sharded Data Parallel) and ZeRO — modern techniques that get many model-parallelism benefits with a data-parallelism-like programming model (deeper coverage in the Multi-GPU Training with PyTorch DDP — Practical Walkthrough — Interactive Explainer).

Multi-GPU Training with PyTorch DDP — Practical Walkthrough — Interactive Explainer ↗
End-to-end walkthrough of distributed training in PyTorch. The DDP mental model: one Python process per GPU; each process runs the same script with its own rank. The setup: torch.distributed.init_process_group() at script start, torch.nn.parallel.DistributedDataParallel(model) wraps your model. The DistributedSampler: ensures each GPU sees a different slice of the data so the union covers the whole dataset. Without it, all GPUs would see the same data and you'd be doing redundant work. The launcher: torchrun (modern) replaces torch.distributed.launch (legacy). Command: `torchrun --nproc_per_node=4 train.py`. Inside the script, accessing the rank via int(os.environ['LOCAL_RANK']). The 'rank-zero only' pattern: only rank 0 should print, save checkpoints, log to W&B, etc. Otherwise you get 4 copies of every log line and 4 attempts to write the same file. The all-reduce synchronization: happens automatically inside DDP during backward. Debugging DDP: the dreaded 'NCCL timeout' (one process is stuck), 'mismatched output sizes' (you forgot DistributedSampler), 'deadlock on barrier' (one process is doing something the others aren't). Mixed precision + DDP: works seamlessly, GradScaler is rank-aware. Brief mention of FSDP (Fully Sharded Data Parallel) — a PyTorch native option for very large models that combines data parallelism with parameter sharding, similar to ZeRO. When to graduate to FSDP: when your model is too big for vanilla DDP. Common pitfalls: forgetting init_process_group, using a non-distributed sampler, all ranks trying to save checkpoints, mismatched code on different ranks (e.g., if rank 0 logs and others don't have the log directory).

Hyperparameters Overview — Interactive Explainer ↗
Mirrors the Loss Functions Overview — Interactive Explainer but for the tuning side. What hyperparameters are: parameters you set BEFORE training (vs parameters the model learns DURING training). The major DL hyperparameters surveyed. Learning rate (the single most important — typical range 1e-4 to 1e-1). Batch size (32 to 1024 typical; interacts with learning rate). Optimizer choice (AdamW for most things, SGD with momentum for some). Weight decay (typical 1e-5 to 1e-3). Momentum (~0.9 for SGD, betas for Adam). Network depth and width. Activation choice (ReLU/GELU/SiLU). Dropout rate (0.1 to 0.5 typical). Number of training epochs (sometimes called 'time budget'). The sensitivity hierarchy: not all hyperparameters matter equally. Learning rate dominates (changing LR by 10x ruins or saves a run); batch size and weight decay are second-tier; depth/width matter but the effect is gradual; most others are minor tweaks. Interactive visualization: a 'sensitivity bar chart' showing how much each hyperparameter affects a target metric, based on real ablation studies. Tuning Strategies — Grid, Random, Bayesian Search — Interactive Explainer ↗
How to actually search the hyperparameter space. Grid search: try all combinations of a small set of values for each hyperparameter. 4 LRs × 3 batch sizes × 3 weight decays = 36 runs. Pros: thorough. Cons: cost scales exponentially with number of hyperparameters; spends compute on dimensions that don't matter. Random search: sample each hyperparameter independently from its range. 36 random samples. Pros: same cost as grid but better. The Bergstra-Bengio 2012 result: random search dominates grid search in high dimensions because it spreads samples across the important dimensions. Visual demo: 2D hyperparameter space where dimension A is the only one that matters; grid wastes 5/6 of its budget on dimension B, random doesn't. Bayesian optimization: use observed results to fit a surrogate model (typically a Gaussian Process); pick the next hyperparameter to try that maximizes expected improvement. Pros: dramatically better sample efficiency. Cons: serial nature limits parallelism. Implementations: optuna, hyperopt, Ax/BoTorch. Population-based training (DeepMind): run many parallel trials, periodically copy weights+hyperparameters from good runs to bad runs and perturb. Effectively explores the hyperparameter space while training. Used for RLHF and LLM tuning at scale. The 'LR finder' technique (Leslie Smith): a clever shortcut for the most-important hyperparameter — train for ~100 steps with exponentially increasing LR, plot loss vs LR, pick the LR where loss decreases fastest. Practical recipe for tuning a typical project: LR finder for LR, then random search over (weight decay, dropout) with cosine schedule, log everything in W&B.

Learning Rate Schedules — Warmup, Cosine, OneCycle, Reduce-on-Plateau — Interactive Explainer ↗
The single most-tuned hyperparameter changes during training — here's how. Why decrease LR over training: early training needs a big LR to escape bad starting regions; late training needs small LR to converge precisely. Constant LR rarely works for serious training. The classic schedules. Step decay: multiply LR by 0.1 every K epochs. Simple, surprisingly effective. Used in older CNN training (e.g., ResNet on ImageNet). Cosine annealing: LR follows half a cosine curve, starting at peak and smoothly decreasing to zero. The modern default for most training. The math: lr(t) = lr_max * 0.5 * (1 + cos(π * t / T_max)). Plus warmup: for the first 1-10% of training, linearly ramp LR from 0 to lr_max, THEN apply the schedule. Critical for Transformers and large models where the initial untrained weights would diverge with full LR. Cosine with restarts (SGDR): periodically reset LR back to peak; can find better minima. OneCycle (Leslie Smith): a complete recipe — warmup to lr_max, then anneal to a much smaller value over the rest of training, plus momentum schedule going the opposite direction. Reduce on plateau: monitor validation loss; if it hasn't improved for K epochs, divide LR by 10. Adaptive but reactive. Compared to schedule-based which are predictive. Interactive: plot any schedule with sliders for max LR, warmup steps, total steps. PyTorch implementations: torch.optim.lr_scheduler offers all of these. The scheduler.step() placement gotcha: call it after optimizer.step(), not before. Per-batch vs per-epoch scheduling: cosine is usually per-batch (smoother), reduce-on-plateau is per-epoch (less noisy).

Experiment Tracking — Weights & Biases, MLflow, Reproducibility — Interactive Explainer ↗
How to keep track of 100 training runs without going insane. The problem: you try LR 1e-3, batch 32; then LR 1e-4, batch 64; then... 50 variations later, which one was best? What were its hyperparameters? Is the model still saved? Without tracking infrastructure, ML becomes 'cargo cult what kinda worked last time.' Modern tracking tools. Weights & Biases (wandb): cloud-hosted, pretty dashboards, real-time plotting, model registry, sweeps for hyperparameter search. The de facto standard for academic and industry DL work. MLflow: open-source, self-hostable, less polished UI but better governance for enterprise use. TensorBoard: free, basic, runs locally; included with PyTorch. Aim, Comet, Neptune: alternatives with various trade-offs. What to log. Every hyperparameter (training config). Every metric (train/val loss, accuracy, F1, etc.) at each step. Sample inputs and outputs (e.g., predicted images, generated text). System metrics (GPU utilization, memory, throughput). Model architecture and parameter counts. Git commit SHA for code reproducibility. Random seeds. The reproducibility problem. Even with all this logged, exactly reproducing a run is hard: CUDA non-determinism, library version drift, hardware differences. Best practices: pin all library versions, set random seeds in torch/numpy/python, use torch.use_deterministic_algorithms() for full determinism (at compute cost). The recommended workflow: every training run logs to wandb, every code change is committed, every successful run gets tagged for easy retrieval, periodic 'what did I learn?' review of past sweeps.

Evaluation Metrics for Regression — Interactive Explainer ↗
Parallel companion to Evaluation Metrics for Classification — Interactive Explainer, but for continuous outputs. The fundamental difference: classification is right-or-wrong; regression is a continuous error. Many ways to summarize that error. Mean Absolute Error (MAE): average of |y_pred - y_true|. Same units as target; robust to outliers. Mean Squared Error (MSE): average of (y_pred - y_true)². Larger penalty for big errors; differentiable everywhere; the loss most regression models are trained with. Root Mean Squared Error (RMSE): sqrt of MSE. Same units as target; still penalizes large errors more than MAE. Mean Absolute Percentage Error (MAPE): mean of |y_pred - y_true| / |y_true|. Scale-invariant; useful when target varies over orders of magnitude. Symmetric MAPE for the divide-by-zero problem when targets are near 0. R² (coefficient of determination): 1 - MSE / Var(y). Says 'what fraction of the variance in y does the model explain?' R² = 0 means 'no better than predicting the mean'; R² = 1 means 'perfect.' R² CAN BE NEGATIVE: if your model is worse than predicting the mean. This usually means a bug. The decomposition R² = Var(y_pred) / Var(y) for a perfect model. Adjusted R²: corrects for number of features in linear models. Less relevant for DL. The diagnostic: residual plots — plot (y_true - y_pred) vs y_true; should look like random noise. Patterns (curves, fans) indicate the model is missing structure. Quantile-quantile plots for normality assumption. Calibration plots for probabilistic regression (predicting mean + variance) — covered in the Model Calibration — Reliability Diagrams, ECE, Temperature Scaling — Interactive Explainer. Practical recipe: report MAE + RMSE + R² for any regression problem; use MAPE only if target is far from zero and you care about relative errors.

Bias-Variance — Diagnosing What's Wrong With Your Model — Interactive Explainer ↗
The classical theory that explains every 'my model isn't working' situation. The decomposition: expected MSE on test data = Bias² + Variance + Irreducible Noise. Bias: the systematic error from the model's structural choices. A linear model fit to clearly nonlinear data has high bias — no matter the dataset, the predictions are systematically wrong. Variance: how much the model changes when you re-sample the training data. An overfit complex model has high variance — different training sets give wildly different predictions on the same test point. Irreducible noise: error from inherent randomness in the data that no model can avoid. The visual intuition: dart-board diagram with four panels (low bias / high bias × low variance / high variance) showing what each combination looks like. High bias = darts cluster but far from center; high variance = darts scattered wildly; both = scattered far from center; neither = tight cluster on center. The bias-variance trade-off: simple models (few parameters) have high bias, low variance; complex models have low bias, high variance. The sweet spot minimizes both. The diagnostic recipe — what loss curves tell you. Both train and val loss high: high bias (underfitting). Get a bigger model or train longer. Train loss low, val loss much higher: high variance (overfitting). Get more data, add regularization, reduce capacity. Both train and val loss reasonable but val noisier than train: high variance but not catastrophic; standard regularization (Dropout & Weight Decay) suffices. Both losses noisy and unstable: implementation bug, exploding gradients, or wrong learning rate. The modern twist: Double Descent (covered in the Network Depth, Width, and Capacity — Interactive Explainer) breaks the classical trade-off in the overparameterized regime — much-bigger models can have BOTH low bias AND low variance. Practical diagnosis: look at your loss curves, match them against the four canonical cases.

Model Calibration — Reliability Diagrams, ECE, Temperature Scaling — Interactive Explainer ↗
When a model says '0.9 confidence,' is it actually right 90% of the time? Often: no. The concept: well-calibrated probabilities match observed frequencies. A weather forecaster saying '70% chance of rain' should be right 70% of the time across all such forecasts. Why DL models are typically over-confident: training with cross-entropy and modern regularization tends to push probabilities toward 1.0 for the predicted class, even when the model is wrong. Confidence and accuracy diverge. Measuring calibration. Reliability diagram: bin predictions by confidence (0.5-0.6, 0.6-0.7, etc.), plot bin's average confidence vs bin's actual accuracy. Perfect calibration = diagonal line. Common pattern: bins above 0.9 confidence have actual accuracy around 0.7 — over-confidence. Expected Calibration Error (ECE): a single number summary — weighted average of |bin confidence - bin accuracy| across all bins. Lower is better. Maximum Calibration Error (MCE): the worst bin's gap. The fix — Temperature Scaling. Add a single trainable parameter T; replace softmax(logits) with softmax(logits / T). Increasing T softens the distribution. Find the T that minimizes ECE on a held-out validation set (small enough that this isn't itself a meaningful hyperparameter tuning). The remarkable result: temperature scaling fixes calibration on most models with one number. Almost-free fix. Cross-references: when calibration matters most — medical (treatment decisions based on predicted probabilities), autonomous systems (action probability), financial (loss-sensitive predictions). When it matters less — pure ranking tasks where only relative order matters. The 'over-confidence + selective prediction' workflow: trust predictions above some threshold T, defer the rest to humans. Calibration is what makes this threshold meaningful. Beyond temperature scaling: Platt scaling, isotonic regression, Bayesian neural networks, deep ensembles — covered as briefer mentions for further reading.
