From “a grid of numbers” to a NumPy array

In the What Is an Image? — Interactive Explainer, you clicked on individual pixels and saw their grayscale intensity values. In the Colour — RGB, BGR, HSV, and Grayscale — Interactive Explainer, the same click gave you three numbers per pixel instead of one.

In Python, that whole grid of numbers is a NumPy array — a multidimensional rectangular box of numbers that you can index, slice, and transform with concise syntax. This explainer is where "an image is a grid of numbers" stops being a mental model and becomes numpy.ndarray, a data structure you can manipulate.

Grayscale image
shape = (96, 96)
9,216 numbers total
RGB image
shape = (96, 96, 3)
27,648 numbers total

Two layouts to remember:

Grayscale = 2D array: shape = (height, width) — one number per pixel.
RGB = 3D array: shape = (height, width, 3) — three numbers per pixel, one per colour channel.

Throughout this explainer we'll use NumPy's row-major convention: the first axis is height (rows, top-to-bottom), the second is width (columns, left-to-right), and (for RGB) the third is channel (R, G, B in that order). The pixel data type is typically uint8 — 8-bit unsigned integers in the range 0–255, exactly as the first explainer introduced. We'll come back to data types and their consequences in §6.

Why NumPy specifically? Every Python image library — PIL, OpenCV, scikit-image, torchvision — eventually represents images as NumPy arrays under the hood. Learning to think in NumPy array terms is learning to think in the universal Python image format.

Reading a pixel: img[row, col]

The simplest possible operation. Click any cell in the 16×16 region from the kitten's face, and watch what Python returns from the corresponding indexing expression:

The Python expression
Click a cell to read its value.

Two patterns to internalize:

For an RGB image: img[row, col] returns a length-3 array — one number per channel: array([R, G, B]).
For a grayscale image: img[row, col] returns a single number — the intensity.

The order is always row first, then column. This is the NumPy / PyTorch convention you saw in the first explainer's coordinate-systems discussion. Some other libraries (notably OpenCV's drawing functions) use (x, y) instead — column first, then row. Mixing them up is the source of the most common indexing bug in CV code.

To read a specific channel of a specific pixel, you add a third index:

img[5, 8, 0] # the red value at row 5, col 8 img[5, 8, 1] # the green value img[5, 8, 2] # the blue value

These three values together are exactly what you see in the readout above when you click a cell.

Reading a region: slicing

Reading one pixel is fine, but most CV operations work on regions — many pixels at once. NumPy uses Python's slice syntax for this: start:stop:step on each axis. Here are the three patterns you'll use most often, with concrete results on a 192×192 kitten:

img[10:50, 20:80]
crop a rectangular region
result shape: (40, 60, 3)
img[:, :, 0]
extract the red channel
result shape: (192, 192)
img[:, ::-1]
flip horizontally
result shape: (192, 192, 3)

Three things to notice. First, a colon by itself (:) means "all of this axis" — so img[:, :, 0] reads "all rows, all columns, channel index 0." Second, slicing reduces dimensionality when you use a single index but preserves it when you use a range — img[:, :, 0] gives a 2D array but img[:, :, 0:1] keeps the third axis with size 1. Third, a negative step like ::-1 reverses an axis — a trick we'll use again in §5.

A small reference of slice patterns
img[10:50, 20:80] # rectangular crop img[:, :, 0] # red channel (2D result) img[:, :, ::-1] # reverse channel order: RGB → BGR img[::2, ::2] # every second pixel (4× downsample) img[:, ::-1] # horizontal flip (mirror) img[::-1, :] # vertical flip (upside-down)

All of these are view operations — they don't copy memory by default; they just give you a different way of looking at the same underlying data. That's why they're extremely fast even on large images.

The Basic Image Operations — Resize, Crop, Rotate, Flip — Interactive Explainer later in this category goes deeper into the practical use of these operations — including interpolation choices for resizing, which slice syntax alone doesn't cover.

Vectorisation — why NumPy at all

Python loops are slow. If you write a loop that visits every pixel of even a moderately-sized image, you'll wait noticeably long for it to finish. NumPy's superpower is vectorisation — applying an operation to every element of an array in a single function call that runs in tight, compiled C code under the hood.

Concrete example: brighten every pixel of a 224×224 RGB image by 30.

The slow way (naive Python loop)
def brighten_naive(img, n): out = img.copy() h, w, c = img.shape for y in range(h): for x in range(w): for ch in range(c): out[y, x, ch] = min(int(img[y, x, ch]) + n, 255) return out
The fast way (vectorised NumPy)
def brighten_vec(img, n): return np.clip(img.astype(np.int16) + n, 0, 255).astype(np.uint8)

Both functions produce identical output. But on the same 224×224 image:

Naive loop
~55 ms
Vectorised
~0.034 ms
Same result, ~1,600× faster. The naive version visits 150,528 pixels one at a time in Python; the vectorised version hands the entire array to a single C function.

This speedup matters more than it first appears. Training a CNN involves applying preprocessing to thousands of images per second — a 1,600× speedup on each one is the difference between a model that trains overnight and a model that doesn't train at all. Every PyTorch image-augmentation pipeline you'll encounter is built on vectorised NumPy or its GPU equivalent.

The rule of thumb: if you find yourself writing a for loop over pixel coordinates, pause and look for the vectorised equivalent. NumPy has direct functions for nearly every common operation — addition, multiplication, clipping, masking, comparison, sorting — and they all work on whole arrays at once.

The full pipeline as one expression: np.clip(img[80:160, 30:130, :][:, ::-1].astype(np.int16) + 40, 0, 255).astype(np.uint8)[:, :, [2, 1, 0]] — all four operations chained together. This is what makes NumPy concise: a sequence of slices, arithmetic, and conversions can produce a final image without ever writing a loop.

The uint8 wraparound trap

You may have noticed that the vectorised brighten function in §4 did something extra: .astype(np.int16) + n before clipping. Why convert to int16 first instead of just writing img + n?

Try it both ways and see what happens. The slider below adds N to every pixel of the kitten. On the left: the naive way (img + N with uint8 arithmetic). On the right: the correct way (np.clip(img + N, 0, 255)). Drag the slider and watch.

0
✘ img + N (uint8 wraps)
pixel = (orig + N) % 256
✔ np.clip(img + N, 0, 255)
pixel = min(orig + N, 255)

Around N=10 the white fur starts developing black holes. By N=60 the image is barely recognisable — bright regions have turned into dark spots, sometimes with completely wrong colours. This is integer wraparound: when an arithmetic result exceeds the maximum value of the data type, it wraps back to zero instead of saturating. For uint8:

uint8(240) + uint8(30) → uint8(14) # wrong! 270 wraps to 14 uint8(255) + uint8(1) → uint8(0) # wrong! 256 wraps to 0

The fix has two parts. First, do the arithmetic in a wider type (int16 or int32) that can hold values above 255. Then use np.clip to saturate values back into the 0–255 range before converting to uint8:

# Wrong: stays in uint8, wraps result = img + n # Right: widen, add, clip, convert back result = np.clip(img.astype(np.int16) + n, 0, 255).astype(np.uint8)

This is the same conceptual problem you have any time you do arithmetic on integer types whose range you might exceed. NumPy follows C's integer-overflow conventions because itis running C arithmetic. So does JavaScript's Uint8Array (in fact the wraparound demo above is running the same buggy math in your browser, not just simulating it).

This is why neural networks always use float32, not uint8. Floating-point arithmetic doesn't wrap around — it has effectively infinite range for image-scale values. PyTorch's transforms.ToTensor() automatically converts uint8 arrays to float32 tensors with values in 0.0–1.0, sidestepping this entire class of bug. We'll see exactly that conversion in §7.

From NumPy to PyTorch tensors

The final move. Every PyTorch CNN you'll meet later in this roadmap expects images as PyTorch tensors, not NumPy arrays. The conversion is one line of code, but it changes three things at once — the data type, the value range, and the axis order.

What transforms.ToTensor() does

1. Converts uint8 (0–255) to float32 (0.0–1.0) by dividing every value by 255.
2. Reorders axes from (H, W, C) (NumPy convention) to (C, H, W) (PyTorch convention).
3. Converts from NumPy array to PyTorch Tensor.

In code:

import numpy as np from torchvision import transforms img_np = np.array(pil_image) # shape (H, W, 3), dtype uint8, values 0-255 img_pt = transforms.ToTensor()(img_np) # shape (3, H, W), dtype float32, values 0.0-1.0

The axis reorder is the most surprising change. Visually:

↓

Why the axis flip? Because The Convolution Operation — Interactive Explainer processes each channel as a contiguous 2D slab of memory, and putting channels first makes each channel-slab a contiguous block in memory. This drastically improves cache locality and GPU throughput — typically 2–3× faster than processing channels-last data.

Going the other way: PyTorch tensor → NumPy array

You'll often need to convert back — for example, to display a model's output with matplotlib (which expects (H, W, C) NumPy arrays):

# Tensor in (3, H, W) float32 → NumPy in (H, W, 3) uint8 for display img_back = (img_pt.permute(1, 2, 0).numpy() * 255).astype(np.uint8)

.permute(1, 2, 0) rearranges the axes: axis 1 (H) becomes the new first axis, axis 2 (W) becomes the new second, axis 0 (C) moves to the end. The result is the original NumPy layout you can pass straight to plt.imshow.

What you can now do

You can read individual pixel values, slice out regions and channels, chain transformations together vectorised, avoid the integer-wraparound trap, and move data fluently between NumPy and PyTorch. That's the everyday toolkit for handling image data in Python.

Up next: the Loading, Displaying, and Saving Images — Interactive Explainer shows how images actually get into and out of these NumPy arrays from disk — the practical file-IO layer beneath every CV pipeline.

The mental model that holds: when you see code like img[16:80, 30:130, :] in any CV codebase from this point on, you know exactly what it's doing — a region of pixels, every channel, returning a sub-array of the original image. The syntax was never the hard part. Knowing what the array is — a grid of numbers indexed by row, column, channel — was the hard part. And you've had that since the first explainer.
