From a file on disk to a grid of numbers

In the Images as NumPy Arrays — Interactive Explainer, an image was a numpy.ndarray of shape (H, W, 3) — a tidy box of uint8 numbers you could slice and transform. But open your photos folder and look at the actual file: sunset.jpg is not a grid of numbers. It is a compressed bitstream — a sequence of bytes that follows the JPEG format's rules.

So “loading an image” is really one specific operation: decoding. A library reads those bytes, runs the JPEG (or PNG, or WebP) decoding algorithm, and hands you back the array you already know how to work with. “Saving” is the reverse: encoding an array into compressed bytes.

Those leading bytes FF D8 FF are not decoration — they are the JPEG magic number, the signature every JPEG file starts with. PNG files start with the 8-byte signature 89 50 4E 47 0D 0A 1A 0A — the 50 4E 47 in the middle is PNG in ASCII, and the leading 89 is deliberately a non-ASCII byte so the file is never mistaken for plain text. This is how a library knows which decoding algorithm to run, regardless of the file extension.

The key reframe: you never “open an image” directly. You decode a file into an array, do your work on the array (everything from the Images as NumPy Arrays — Interactive Explainer), then encode the array back into a file. The array is the thing you compute on; the file is just how it's stored and shared.

The Python image-library landscape

Four libraries do the decode/encode work in Python. They overlap a lot, but each was built with a different priority. You don't need all four for every project — but you'll meet all four in real code, so here's what each is for.

PIL / Pillow

The general-purpose default

The most common Python image library. Opens almost any format, simple API. Its Image object is not a NumPy array — it's PIL's own type.

type: PIL.Image.Image
channel order: RGB
OpenCV (cv2)

The CV powerhouse

Faster than PIL on large images and packed with computer-vision functions. Two famous gotchas: it loads as BGR, not RGB, and its display window only works in scripts, not notebooks.

type: numpy.ndarray
channel order: BGR
torchvision

The PyTorch on-ramp

Loads images straight into PyTorch tensors in (C, H, W) order — ready for a neural network with no conversion step.

type: torch.Tensor
shape: (3, H, W)
Matplotlib

The notebook display tool

Not really for loading — it's for showing. plt.imshow(arr) is the universal “display this array in my notebook” command. It expects RGB.

role: display
expects: RGB

Here is the same file loaded by each library. Notice they hand back different types, but each ultimately wraps the same grid of pixel values:

# PIL/Pillow → a PIL Image object (RGB) from PIL import Image img_pil = Image.open("sunset.jpg") # <PIL.Image.Image, RGB, 480x320> # OpenCV → a NumPy array, but in BGR order import cv2 img_cv = cv2.imread("sunset.jpg") # ndarray (320, 480, 3), BGR # torchvision → a PyTorch tensor in (C, H, W) order from torchvision.io import read_image img_tv = read_image("sunset.jpg") # tensor (3, 320, 480), RGB # Matplotlib → for showing, not loading import matplotlib.pyplot as plt plt.imshow(img_pil); plt.show() # renders in the notebook
Every loader gives you the same pixels — but in different containers (PIL object vs ndarray vs tensor) and sometimes different channel order (RGB vs BGR) and axis order (HWC vs CHW). The next two sections are about moving between those containers, and the colour bug that the BGR difference causes.

The PIL ↔ NumPy ↔ tensor bridge

Because the libraries use different containers, real code constantly converts between them. There are really just three containers and a handful of one-line conversions connecting them. Here is the whole map:

The PIL ↔ NumPy hop is the one you'll use most:

import numpy as np from PIL import Image img = Image.open("sunset.jpg") # PIL Image arr = np.array(img) # → ndarray (320, 480, 3), now you can slice it # ... do NumPy work from the previous explainer ... arr[:, :, 0] = 0 # zero out the red channel back = Image.fromarray(arr) # ndarray → PIL Image, ready to .save()

The NumPy ↔ tensor hop has one extra wrinkle you already met in the Images as NumPy Arrays — Interactive Explainer: NumPy uses (H, W, C) but PyTorch wants (C, H, W). So the conversion is paired with a .permute() to reorder the axes:

import torch # NumPy (H, W, C) → tensor (C, H, W) t = torch.from_numpy(arr).permute(2, 0, 1) # (320,480,3) → (3,320,480) # tensor (C, H, W) → NumPy (H, W, C) arr2 = t.permute(1, 2, 0).numpy() # back to (320,480,3)
You don't need to memorise every arrow. Remember the shape of the map: three containers (PIL Image, ndarray, tensor), NumPy in the middle as the universal hub, and the (H,W,C) ↔ (C,H,W) axis-swap whenever PyTorch is involved.

The BGR trap, made concrete

In the Colour — RGB, BGR, HSV, and Grayscale — Interactive Explainer, you learned that OpenCV stores channels as BGR while almost everything else uses RGB. That fact sounds harmless until you hit the bug it causes — which every beginner does exactly once. Here it is, live.

You load an image with OpenCV (so the array is in BGR order) and display it with Matplotlib (which assumes RGB). Matplotlib reads the blue channel as if it were red, and the red as if it were blue. The result:

Correct (RGB)
Wrong: cv2.imread shown by plt.imshow

The warm orange sunset turns cold and blue, because the orange (high red, low blue) becomes high-blue-low-red. The fix is one line — convert the channel order before displaying:

import cv2 import matplotlib.pyplot as plt img = cv2.imread("sunset.jpg") # BGR order # WRONG — plt assumes RGB, so colours are swapped plt.imshow(img) # RIGHT — convert BGR → RGB first img_rgb = cv2.cvtColor(img, cv2.COLOR_BGR2RGB) plt.imshow(img_rgb) # correct colours # Equivalent NumPy-only fix (reverse the channel axis): img_rgb = img[:, :, ::-1] # callback to slicing from the NumPy explainer
The bug is invisible in code — no error, no crash, just wrong colours. The tell-tale sign is a photo where blue and red look swapped (skies turn orange, skin turns blue). Whenever you mix cv2 with anything else, ask: “is this array RGB or BGR right now?”

Displaying: notebook vs script

“Show me this image” sounds like one operation, but where you run your code changes which tool works. Displaying an image means: interpret an array as colours and paint its pixels onto some surface — a notebook output cell, or a pop-up window. Those are two different surfaces, and they need different tools.

ToolWorks in Jupyter notebook?Works in a .py script?Notes
plt.imshow(arr) Yes — the standard Yes (with plt.show()) Universal. Expects RGB. Best default for learning.
cv2.imshow(win, arr) No — hangs / crashes the kernel Yes (with cv2.waitKey) Opens a native OS window. Needs an event loop a notebook doesn't have. Expects BGR.
img_pil.show() Opens external viewer Yes Launches your OS's default image app. Fine for a quick look.
display(img_pil) Yes — inline No Jupyter's built-in. Renders a PIL Image right in the cell.

The classic trap is cv2.imshow in a notebook. In a standalone script it opens a window and cv2.waitKey(0) keeps it open until you press a key:

# In a .py SCRIPT — this works: import cv2 img = cv2.imread("sunset.jpg") cv2.imshow("window", img) # opens a native window (shows BGR correctly) cv2.waitKey(0) # wait for a keypress cv2.destroyAllWindows() # In a NOTEBOOK — do this instead: import matplotlib.pyplot as plt img_rgb = cv2.cvtColor(img, cv2.COLOR_BGR2RGB) # fix the colour order first! plt.imshow(img_rgb) plt.axis("off"); plt.show()
Rule of thumb for learning: use plt.imshow for everything, and remember to convert BGR→RGB first if the array came from OpenCV. Save cv2.imshow for standalone scripts where you want a real interactive window.

Saving images: encoding an array back to a file

Loading was decode: file→array. Saving is the mirror image — encode: array→file. Each of the four libraries has its own one-line save call, and each carries the same quirks (channel order, axis order, value range) you met when loading. Here they are side by side.

LibrarySave callExpectsWatch out for
PIL img.save("out.png") A PIL Image object Format is inferred from the file extension. Convert from a NumPy array first with Image.fromarray.
OpenCV cv2.imwrite("out.png", arr) A NumPy array in BGR If your array is RGB, convert first — otherwise the saved file has red and blue swapped. Returns True/False, it doesn't raise on failure.
torchvision save_image(t, "out.png") A float tensor in [0, 1], shape (C, H, W) A uint8 [0,255] tensor comes out almost black — divide by 255 first.
Matplotlib plt.imsave("out.png", arr) A NumPy array in RGB Saves just the image data (no axes/titles). Use this, not savefig, when you want the raw image.

In code, the same edited array saved four ways:

# PIL — from a NumPy array, format from extension from PIL import Image Image.fromarray(arr).save("out.png") # arr is RGB uint8 (H,W,3) # OpenCV — expects BGR, so convert if your array is RGB import cv2 bgr = cv2.cvtColor(arr, cv2.COLOR_RGB2BGR) cv2.imwrite("out.png", bgr) # returns True on success # torchvision — expects a FLOAT tensor in [0,1], shape (C,H,W) from torchvision.utils import save_image save_image(t.float() / 255, "out.png") # t is a uint8 (C,H,W) tensor # Matplotlib — expects RGB, writes just the pixels import matplotlib.pyplot as plt plt.imsave("out.png", arr) # arr is RGB
Saving repeats the loading lesson in reverse: each library wants the array in its preferred form before it will encode correctly. OpenCV wants BGR, torchvision wants a float (C,H,W) tensor in [0,1], PIL and Matplotlib want RGB. Match the form and the saved file is correct; mismatch it and you get swapped colours or a near-black image — with no error message to warn you.

Lossy vs lossless: what compression actually does

A raw, uncompressed image takes one byte per channel per pixel. Our 460 000-pixel sample would be 450.0 KB raw. Nobody stores photos like that — compression shrinks them dramatically. There are two kinds, and the difference matters.

Lossless (PNG, WebP-lossless): throws away nothing. Decode it and you get back the exact original array, byte for byte. Lossy (JPEG, WebP): throws away detail your eye barely notices, in exchange for much smaller files. The catch: once discarded, that detail is gone forever.

Saving at a chosen quality is one argument:

from PIL import Image img = Image.open("sunset.png") img.save("out.jpg", quality=90) # lossy, small, great for photos img.save("out.png") # lossless, exact, great for sharp edges img.save("out.webp", quality=90) # modern, smaller than JPEG
“JPEG quality 90” isn't a unit of goodness — it's a dial trading file size against discarded detail. Quality 90 is near-invisible loss for photos; quality 20 is tiny files with obvious artifacts. And the content matters: photos compress beautifully with JPEG, but anything with crisp edges or text is better as PNG.
